# pfSense PHP-FPM memory hardening

## Incident context — 2026-09-08

The Netgate 1100 running pfSense 26.07-RELEASE suffered coupled CPU and memory
pressure while the homelab was polling pfREST through `pfsense-exporter`.
Runtime evidence showed nginx still listening on TCP/10443 while PHP-FPM was
unavailable, pfREST returned 502, Unbound had previously been killed by the
kernel under memory pressure, and the WebConfigurator became unusable.

Measured platform memory:

```text
hw.realmem = 1073680384 bytes  (~1024 MiB)
hw.physmem = 1010601984 bytes  (~964 MiB)
avail boot =  985812992 bytes  (~940 MiB)
```

pfSense sizes the `REALMEM > 1000` PHP-FPM profile in
`/etc/rc.php_ini_setup` as:

```text
PHPFPMMAX=8
PHPFPMIDLE=3600
PHPFPMSTART=2
PHPFPMSPARE=7
PHPFPMREQ=5000
```

On this appliance the eight PHP-FPM workers were observed around 48-65 MiB RSS
each during sustained pfREST activity. The nominal 1 GiB sizing branch therefore
leaves too little practical headroom for Unbound/pfBlockerNG, HAProxy and other
critical edge services.

The WebConfigurator **Max Processes** setting is separate. A configured value of
`2` produced three nginx workers through `system/webgui/max_procs`; it did not
change the PHP-FPM `8/7` sizing generated by `rc.php_ini_setup`.

## Reviewed constrained profile

The Nabla profile for this specific appliance is:

```text
PHPFPMMAX=4
PHPFPMIDLE=30
PHPFPMSTART=1
PHPFPMSPARE=2
PHPFPMREQ=500
```

This controls both resident worker count and recycling pressure. It is paired
with the separate pfSense telemetry budget in `scripts/observability/README.md`:
120-second Prometheus scrape, 8-second exporter target timeout, collector
concurrency 1, and only the essential `system`, `gateways`, and `service`
collectors.

## Repository-managed hardening

Use `scripts/security/harden-pfsense-php-fpm.sh` on pfSense itself. The script is
fail-closed and supports three modes:

```text
--check    read-only source/runtime validation
--apply    backup, patch, regenerate, restart, validate
--restore  restore the saved generator and regenerate/restart
```

The mutation path is intentionally restricted to `26.07-RELEASE` and to the
reviewed upstream source profile `8/3600/2/7/5000`. It performs exactly five
assignment substitutions inside the `REALMEM > 1000` branch. Any unexpected
source shape aborts the change.

The first apply stores the rollback copy at:

```text
/conf/backup/rc.php_ini_setup.nabla-pre-phpfpm-hardening
```

The apply sequence then:

1. changes only the reviewed high-memory generator branch;
2. runs the OS-managed `/etc/rc.php_ini_setup` through its shebang interpreter when the file is not executable;
3. requires the generated profile to be exactly `4/30/1/2/500`;
4. restarts PHP-FPM with `/etc/rc.php-fpm_restart`;
5. requires `/var/run/php-fpm.socket` to exist;
6. restarts the WebConfigurator with `/etc/rc.restart_webgui`;
7. counts `php-fpm: pool nginx` workers with portable `ps` + `awk` and refuses success above four.

Do **not** replace these pfSense-native restart paths with a plain
`php-fpm -y /usr/local/lib/php-fpm.conf`. During the incident that direct launch
failed because the generated pool runs as root and the pfSense wrapper supplies
the required runtime flags.

## Runtime lessons from the first two applies

Two portability failures were found by running the hardening on the actual
26.07-RELEASE appliance and are kept here as regression knowledge:

1. `/etc/rc.php_ini_setup` exists but is not directly executable on this host.
   Invoking it as a command returned `Permission denied` after the source patch
   had already been written. The helper is intentionally idempotent, so the next
   run recognized source `4/30/1/2/500`, invoked the generator via its
   interpreter and completed regeneration.
2. FreeBSD/pfSense `pgrep` is not GNU `pgrep`. The original `pgrep -fc` worker
   validation produced an empty/NaN value and a shell `bad number` error even
   though the PHP-FPM restart itself succeeded. Worker validation now uses
   `ps axww -o command=` piped to `awk`, always producing a numeric count.

After the corrected generator invocation, the real generated runtime was:

```text
pm.process_idle_timeout = 30
pm.max_children = 4
pm.start_servers = 1
pm.max_requests = 500
pm.min_spare_servers = 1
pm.max_spare_servers = 2
```

and the observed steady state immediately after restart was two nginx PHP-FPM
workers around 35 MiB RSS each, instead of eight workers around 48-65 MiB each.
Unbound remained up and `drill @172.17.0.1 example.com A` returned `NOERROR`.

## FastCGI backlog evidence

The incident log also contained repeated kernel messages of the form:

```text
sonewconn: ... local:/var/run/php-fpm.socket: Listen queue overflow: 193 already in queue awaiting acceptance
```

with bursts reaching dozens of additional rejected/queued connection attempts.
This is evidence that the failure was not only resident-memory sizing: pfREST
request fan-out was able to saturate the FastCGI socket backlog while PHP-FPM was
resource constrained. The pfSense exporter must therefore remain stopped during
stabilization. Re-enable telemetry only after PHP-FPM/Unbound memory headroom is
stable, and keep exporter collection serialized and rate-limited.

The historical `dmesg` tail still contains the earlier OOM kills:

```text
netstat ... killed: failed to reclaim memory
unbound ... killed: failed to reclaim memory
```

Do not interpret those old lines as a new OOM event without comparing timestamps
or collecting new kernel messages after the constrained profile was applied.

## Upgrade contract

`/etc/rc.php_ini_setup` is an operating-system managed file. A pfSense upgrade
can replace it. The hardening is therefore persistent for the current installed
release but must be treated as a **reconciled host patch**, not an upstream
configuration option.

After every pfSense upgrade:

1. run `--check` before any mutation;
2. if the release or source profile changed, do not force the patch;
3. review the new upstream sizing logic and update this repository first;
4. only then apply a newly reviewed hardening profile.

This is preferable to an unconditional boot-time `sed` because an upstream
layout change fails visibly instead of silently corrupting the generated PHP-FPM
configuration.

## Runtime acceptance

After `--apply`, validate the constrained pool and critical services before
re-enabling Snort or increasing observability load:

```text
PHP-FPM children <= 4
PHP-FPM socket present
WebConfigurator :10443 reachable
pfREST core GET endpoints return 200
Unbound process/control socket healthy
public recursive DNS returns NOERROR
private int.albandrieu.com delegation still resolves
no new kernel OOM/reclaim kill events after the hardening timestamp
no sustained php-fpm.socket listen queue overflow
```

Keep Unbound out of Service Watchdog while memory pressure remains a plausible
failure mode. A process-only restart loop can amplify allocation pressure and
cannot detect a resolver that is alive but returning functional DNS failures.


## October 25 recurrence: verify actual PHP-FPM workers before removing security

New Netgate 1100 read-only sampling on 2026-10-25 21:37–21:40 CET showed
**8 processes in the broad `php_fpm` group**, accounting for about
**283–307 MiB aggregate RSS** (RSS double-counts shared pages).
The sampler groups `comm` names beginning with `php-fpm`; this is **not
equivalent to 8 pool workers**. It may include the PHP-FPM master.
Do not assert the prior generator patch was lost on this evidence alone.

Use the new workstation read-only recipes:

```bash
just pfsense-php-fpm-test
just pfsense-php-fpm-check
```

`pfsense-php-fpm-check` transfers only the reviewed `--check` script
through SSH. It **does not install anything, restart PHP-FPM, restart
WebConfigurator or alter pfSense**. It reports three independent signals:

1. Generator `>1000 MiB` profile in `/etc/rc.php_ini_setup`.
2. Generated `/usr/local/lib/php-fpm.conf` values.
3. Actual `php-fpm: pool nginx` child count (excluding master).

If generator and generated pool differ, classify this as **configuration
drift**, not as a license to restart production services immediately.
If both are already `4/30/1/2/500` but the pool still has more than
four workers, inspect runtime process ownership and pfSense state first.
If both are at upstream `8/3600/2/7/5000`, apply the documented
constrained profile only in a reviewed maintenance window using the
version-guarded `--apply` and its backup/restore path; never auto-apply
from a read-only audit. Recheck pfREST/WebConfigurator and Unbound DNS.

The historical 2026-09-08 improvement and target remain applicable only
to the reviewed `26.07-RELEASE` generator. A newer pfSense release may
have a different script layout and must fail closed.

### Decision order to protect DNS and retain security coverage

1. **P0 PHP-FPM:** diagnose generator/runtime drift; reduce idle workers
   using the reviewed profile when eligible. This was more material
   historically than dropping individual Snort signatures.
2. **P1 firewall/telemetry:** avoid high-frequency pfREST fan-out and
   excess PF pass logging; verify CrowdSec input/CPU backpressure.
3. **P2 Snort:** keep the WAN-only instance and 32 MiB HTTP Inspect cap;
   verify the low-memory AC-BNFA matching engine before changing rule
   categories. Disabled categories reduce signature coverage; quantify
   relevance and validate LAN/WAN probes before any change.
4. **P2 pfBlockerNG:** keep previously disabled UT1 Adult and obsolete
   feeds disabled, avoid re-enabling DNSBL TLD, and verify ASN reporting
   is still disabled when no IPinfo token/database contract exists.
   Classify stale HTTP 403/404 and log retry lines as maintenance debt,
   not proof of present RAM exhaustion.

Do **not** disable Unbound, all DNSBL or all WAN Snort as the default
memory optimization; do not raise PHP memory_limit from 128M as a
workaround for a large DNSBL file.

### Prepared workstation workflow

Scripts in PR #280 provide explicit, guarded commands:

```bash
just pfsense-php-fpm-test
just pfsense-php-fpm-check
just pfsense-security-capacity-audit
```

The new read-only audit detects generator/runtime drift and actual
nginx workers, verifies local Unbound control and DNS `NOERROR`,
and reports CrowdSec bouncer presence without restarting it.

**Apply only in a separate maintenance window**, not during
pfBlockerNG at 00:00, 04:00, 22:00 or Snort at 02:09/14:09.
Have SSH/serial fallback and verify management-access restrictions.

```bash
PFSENSE_PHP_FPM_CHANGE_CONFIRM=APPLY_4_WORKERS just pfsense-php-fpm-apply
```

This requires explicit confirmation and a remote privileged
non-interactive shell (root or passwordless `sudo -n`). It:

1. Rejects invalid args, host or unauthorized change *before SSH*.
2. Preflights running Unbound, its control socket and an actual
   `NOERROR` DNS response from 127.0.0.1. **Apply refuses when
   Unbound is unverified**, particularly after the recent outage.
3. Uses the previously reviewed version-guarded backup + generator
   hardening script with the **native pfSense** PHP-FPM and webGUI
   restart sequences; no reboot and no CrowdSec/Snort reload.
4. Checks Unbound/DNS, PHP-FPM socket, generated `pm.max_children=4`
   and the actual nginx worker count (1..4). Reports success
   only when the checks complete.

**If maintenance fails**, inspect the failure before running other
service changes. Restore the saved generator using:

```bash
PFSENSE_PHP_FPM_CHANGE_CONFIRM=RESTORE_BACKUP just pfsense-php-fpm-restore
```

The restore is independently guarded and may proceed even when
Unbound is unhealthy, so that DNS faults do not prevent recovery.
The post-restoration DNS smoke can still fail if DNS remains down;
that must not be confused with failure to restore the generator.
The backup is the OS-local file
`/conf/backup/rc.php_ini_setup.nabla-pre-phpfpm-hardening`.

**After applying**, measure memory again with
`just pfsense-memory-window`, validate the webConfigurator
HTTPS, essential pfREST GET operations, localhost and LAN public
and private DNS, then watch for new kernel OOM or php-fpm socket
queue overflow. The improvement target is **at least 128 MiB**
of free+inactive headroom under ordinary load (not an
OOM-free guarantee). Do not increase PHP `memory_limit=128M`.

**GUI distinction (Netgate docs):**
`System > Advanced > Admin Access > webConfigurator > Max Processes`
controls the **web server (nginx)** workers, not PHP-FPM pool
workers. `System > Advanced > Miscellaneous > PHP Settings >
Memory Limit` limits memory **per PHP process**. Neither exposes
the five PHP-FPM sizing values this script reconciles.
Sources:
<https://docs.netgate.com/pfsense/en/latest/config/advanced-admin.html>
<https://docs.netgate.com/pfsense/en/latest/config/advanced-misc.html>.

**Snort performance UI (different component):**
`Services > Snort > Interfaces > Edit WAN > Interface Settings >
Detection Performance Settings > Search Method` should use
**AC-BNFA** on a low-memory appliance; inspect the exact
installed package UI first. Verify the WAN-only instance and
HTTP Inspect memcap of 32 MiB, do not mutate generated
`snort.conf` directly. Netgate docs:
<https://docs.netgate.com/pfsense/en/latest/packages/snort/interface-settings.html>.

**No GitHub Actions paid CI; no changes to pfSense have been
